# Lotion 插件化架构（重构计划）

> 目标：把 Lotion 从"一个 SPA + 一堆直接互相 import 的模块"重构为**插件化应用**——
> 核心只提供接缝与内核，功能以插件形式挂载；每一步都可运行、`pnpm test` 全绿、单独提交。
>
> 设计参照 DeepSeek Harness（`/Users/ky2fe/Project/deepseek-harness`：
> `docs/architecture.zh.md`、`docs/cordis-primer.zh.md`、`docs/capability-seams.zh.md`、
> `docs/cookbook/adding-a-package.zh.md`、`packages/extensions/**`），但**只取可迁移子集**。

## 0. 目标与非目标

**目标**

1. 一个**极简内核**（自研，不引第三方）：具名服务容器 + `inject` 门控 + 可逆副作用 + 四分发模式事件 + 启动 PENDING 审计。
2. **两条真实接缝**（只有当"第二个实现确实会出现"时才立接缝）：
   - `docStore`：文档/会话数据存取（SQLite → 未来 libsql/远程；对应 AGENTS.md 里已注释的 TODO）
   - `config`：两层配置层级（组合默认 + 用户覆盖 + 服务缺失时优雅回退）
3. **装配清单**：`lotion.config.ts` 列出插件（**每项必须有稳定 id**），loader 负责装配、审计、回滚。
4. 现有功能转**内置插件**：路由与 UI 插槽改为注册式，AI 工具注册表去掉 4 处枚举耦合。
5. **opt-in 动态插件通道**（默认关闭）：host 半边 `node:vm`、client 半边动态 import，RPC 白名单边界。用于"AI 在会话内给自己加临时能力"。

**非目标（明确不抄，理由：这些机制只服务"不可预知的第三方"，而 Lotion 是单人全部代码）**

- 双半边包分发 / `__ModuleLoader__` 模块表 / typert 生成式 RPC
- slot 系统的 4 种 kind（只保留 `single` + 有序 `list`）与 42 个 slot 的规模
- per-session preset 子树、Code Mode、generation 安装/回滚、`invariants` 伴生包
- `!!js` 配置表达式（DSH 里它等价于 `eval`，即"配置拥有宿主全权限"——不开这个口子）
- 权限框架：DSH 自己都没有硬约束（`inject` 可被 `ctx.get` 绕过、credentials 无作用域）。
  唯一值得抄的是**客户端 RPC namespace 白名单**。

## 1. 目标架构

```
浏览器进程                                    Node 进程（Hono）
┌─────────────────────────────┐              ┌─────────────────────────────┐
│ client kernel（lib/kernel） │              │ host kernel（lib/kernel）   │
│  ├ docStore: rest provider  │  fetch/REST  │  ├ docStore: sqlite provider│
│  ├ config:  远程读取         │◄────────────►│  ├ config:  文件+默认       │
│  └ uiSlots / tools / commands│              │  └ aiAgent / tools / upload │
└─────────────────────────────┘              └─────────────────────────────┘
        ▲                                                    ▲
        └──────────── 同一个 lib/kernel + 共享契约（类型） ────┘
```

要点：

- **内核是环境无关的纯 TS**（`lib/kernel/`，禁止 `node:` 与 `better-sqlite3`）→ 两个进程共用；
  由现有 `test/boundary.test.ts` 的边界守卫扩展覆盖。
- **契约（服务接口）放客户端安全模块**，实现放各端：`lib/seams/doc-store.ts`（接口）
  ↔ `lib/local/doc-store-sqlite.ts`（host 实现）/ `lib/client/doc-store-rest.ts`（client 实现）。
- 一个 `ctx.<key>` 一个 provider：重复注册**抛错**（这就是"唯一提供方"的全部机制）。

## 2. 内核契约（`lib/kernel/`）

| API | 语义 | 借鉴自 |
|---|---|---|
| `ctx.provide(key, value)` | 注册服务；重复注册抛错 | Cordis `Service` / `ctx.reflect.provide` |
| `ctx.get(key)` | 读服务（缺席返回 `undefined`，用于可选依赖）| Cordis `ctx.get` |
| `ctx.inject(keys, cb)` | **门控**：依赖齐备才执行 `cb`，返回 disposer；依赖消失自动回退 | Cordis `inject` |
| `ctx.plugin(plugin, config)` | 挂载插件（函数 / 带 `apply` 的对象 / Service 子类），返回 fiber | Cordis `registry` |
| `ctx.effect(fn)` | 注册**可逆副作用**：`fn` 返回 disposer，卸载时按记录调用 | Cordis `ctx.effect` |
| `ctx.on/emit/waterfall/parallel/serial` | 四分发模式事件（`emit` 观察 / `waterfall` 环绕中间件 / `parallel` 并行 / `serial` 串行）| `docs/cordis-primer.zh.md:19-27` |
| `ctx.dispose()` | 卸载该插件名下全部注册（工具、监听器、服务、定时器、effect）| Cordis fiber |
| `auditPending(ctx)` | **启动审计**：打印 `PENDING — 缺少服务 …`，避免 `inject` 静默失效 | `docs/cordis-tutorial/06:70-82` |
| `defineService(key, schema?)` | 服务定义助手（含 Config 校验）| `packages/shell/shell/src/index.ts` |

**必须遵守的纪律（DSH 踩过的坑）**

1. 每个注册都要有 disposer；拆卸顺序有要求的工作放进**同一个 effect**。
2. `PENDING` 是合法状态 → 没有 `auditPending()` 的 `inject` 就是静默失败。
3. 注册**就地校验**：非法配置必须在挂载时报错，而不是等到某次请求。
4. 呈现层（UI 卡片）取数据必须是**纯函数**（同一份数据要能用于直播与日志回放）。
5. 守卫用**无 allow 返回域**的类型：`(exec) => string | undefined`（返回即拒绝）→ 顺序无法把 deny 变回 allow。

## 3. 接缝（只立两条）

### 3.1 `docStore`

- **Definition**：`lib/seams/doc-store.ts` —— 抽象类 + 方法签名 + `declare module` 增补 `Context` 的 `docStore` 键。**不是 TS interface**（必须拥有运行期 `ctx.docStore`）。
- **Provider（host）**：`lib/local/doc-store-sqlite.ts` 包 `lib/local/db.ts`（27 个函数）+ `getDb()`。
- **Provider（client）**：`lib/client/doc-store-rest.ts` 包 `lib/db.ts`（21 个函数，走 `/api/*`）。
- **Consumer**：页面、UI 组件、AI 工具。
- 现状清理：`lib/db.ts` 的 `_userId` 形参一律由会话推导 → 从契约里删除（服务端本来就用 cookie 里的 user）。

### 3.2 `config`（两层配置层级）

- 组合层（`lotion.config.ts` + 插件自带默认）为 `base`，用户层（`data/settings.json`）覆盖；
  **设置服务缺失时回退到组合默认而非失败**（`packages/settings/settings/src/index.ts:863`）。
- `Config` 一个声明兼两用：zod schema 既做运行时校验，又是类型来源（zod 4 满足 Standard Schema）。
- 迁移对象：`DEEPSEEK_API_KEY`、`AI_MODEL`、`PORT`、`LOTION_DB_PATH`、`UPLOAD_DIR`、`LOG_LEVEL`
  → 保留 env 作为最高优先级来源（`process.env` > 用户层 > 组合层），env 语义不破坏现有部署。

## 4. 装配清单与生命周期

- `lotion.config.ts`：`[{ id, plugin, config, disabled? }]`，**`id` 必填**（DSH：省略 id 会被铸随机 id，改配置即重新挂载并丢光 effect 状态）。
- 两类层：**live**（用户层 `data/settings.json` 热生效）/ **static**（组合清单，改动需重启）。
- patch 语义：按 id 定位、**整块替换 config**、未知 id 只 warn 不致命（`vendor/include/src/index.ts:58-128`）。
- 失败回滚：装配失败保留上一份可用配置树（`hmr/config-update-failed` 同款语义）。

## 6. 纪律与风险

- **每步单独提交**（`feature:` / `fix:` 中文描述）；后台代码改动**必须**补或更新单测。
- **禁止启动开发服务器**；验证用 `pnpm test` + `pnpm typecheck` + `pnpm lint` + `pnpm build`。
- 行为保持优先：重构阶段不改用户可见行为；UI 视觉改动单独提交。
- 风险 1：内核抽象过早 → 缓解：只实现 P0 表格里那 9 个 API，**不预留**没用到的能力。
- 风险 2：数据格式/接口漂移 → 缓解：契约先冻结（`docStore` 方法名与现有函数一一对应），provider 只做转发。
- 风险 3：动态插件 = 任意代码执行 → 缓解：默认关闭；只收窄 API 面（引导式陷阱 + 门面白名单），**不声称安全边界**；临时插件只存进程内存、不落盘、不自动恢复（照抄 DSH 的产品决策）。

## A.1 一次装配长什么样

```
server/index.ts
```

## A.3 写一个插件（要改哪些文件）

**内置插件（随仓库发布）**

1. 写能力本体（如 `lib/foo.ts`）。
2. 若要贡献接口，在 `lib/seams/<name>.ts` 加契约（类型 + 服务 key + `provide/find/require` + **装配期形状校验**）。
3. 在 `server/composition.ts`（宿主）或 `src/shell/ui-plugins.tsx`（UI）加**一行清单**：`{ id: "<稳定唯一 id>", plugin: {...} }`。
4. 若要贡献路由：`routePlugin` 一行（见 `server/routes/index.ts`）。
5. 若要贡献 AI 工具：`registerTool(ctx, requireTools(ctx), { name, label, icon, description, create, guard? })`。
6. 若要贡献 UI：`requireUiSlots(ctx).register({ id, slot, kind: "single" | "list", component, order? })`。
7. 补单测（`test/` 与源同构）；`pnpm test` 全绿后提交。

**用户侧调整（不改代码）** —— `data/settings.json`：

```json
{
  "ai": { "model": "deepseek-chat" },
  "server": { "port": 3100 },
  "plugins": {
    "dynamic-plugins": { "disabled": false }
  }
}
```

组合清单是**静态层**（改动需重启）；`settings` 走配置层（可热读，AI 模型/Key 每次请求解析，改完即生效）。

## A.4 动态插件通道（默认关闭）

启用：`data/settings.json` 里把 `plugins.dynamic-plugins.disabled` 置为 `false`（一行配置，不改代码）。

启用后模型拿到五个工具：`plugin_inspect` / `plugin_define` / `plugin_run` / `plugin_stop` / `plugin_undefine`。
链路：**定义（只登记）→ 运行（`node:vm` 沙箱求值并挂载）→ 贡献工具/服务 → 停止（等静默）→ 撤销**。
客户端半边：定义被 `approve` 后由 `GET /api/dynamic/plugins` 下发（**只下发 client 代码，绝不下发 host 代码**），
浏览器侧在客户端沙箱里求值并贡献 UI 插槽；宿主没启用时该端点不存在（404）→ 客户端**完全无副作用**。

**安全姿态（如实，别当成沙箱）**：

| 面 | 现状 |
|---|---|
| 宿主半边 | 同进程 `node:vm`：**只收窄 API 面**（教学式陷阱 + ctx 门面白名单 + 服务 inject 白名单），暴露的服务能触达真实运行时 → **与本机 shell 同级信任** |
| 客户端半边 | `new Function` **形参遮蔽**裸标识符；`globalThis.fetch` / `window.setInterval` / `eval` / 动态 import **依然可达**（有单测钉住这一条）→ 故需人工 `approve` |
| 唯一强制的白名单 | **`remote` 接缝**：客户端能调的 namespace/方法是一张枚举表，**没有运行期动态注册路径**；改它必须改代码 |
| 临时性 | 定义只在进程内存：不落盘、重启即消失、永不自动恢复；想常驻就走 A.3 的正常插件流程 |
