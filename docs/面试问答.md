# Lotion 项目面试问答

> 简历项目：全栈笔记应用（Lotion），基于 Next.js + Supabase，集成 DeepSeek AI 笔记助手
> 三个亮点：Agent Tool Call 编排 / 长会话上下文压缩 / 加载性能优化

---

## 第一部分：针对项目三个点的场景题

### 点 1：Agent Tool Call 编排

> 基于 Vercel AI SDK 接入大语言模型，设计 Agent Loop 与 Tool Call 流程，实现对笔记的智能搜索、生成、编辑与归档管理

**Q1. 用户说"把上周关于性能优化的那篇笔记找出来，删掉它"，你的 Agent 会怎么执行？**

**答**：拆解成三步工具调用：

1. **searchNotes**：把用户请求提炼成 2-5 个关键词（如 `性能优化`），服务端 `ILIKE` 按标题模糊匹配，返回最多 20 条结果（id + 标题 + 80 字符摘要）
2. 模型从结果里定位目标笔记 id
3. **deleteNote**：此时工具**不会真删**——它查一下标题后，通过 `onEvent` 上报 `confirm_delete` 事件，前端弹出确认框，用户确认后前端才真正调 `remove()` 落库

**关键点**：删除这类高危操作，我做了「**AI 只能发起、用户才能执行**」的强制确认闸门——模型永远没有直接执行删除的权限，杜绝 AI 误删。

**Q2. 为什么 AI 生成笔记不会出现"重复创建多篇草稿"？**

**答**：两个防线：

1. **工具实例级幂等**：`createNote` 工具闭包里维护 `createdNoteId`，本次对话已创建过笔记时，再次调用直接拒绝并返回"请用该 ID 调 updateNote"。因为工具实例是按请求创建的，闭包状态天然按请求隔离，不需要外部共享对象
2. **会话级提示词约束**：系统提示词里写明"每次对话最多创建一篇笔记"

第 1 条是硬保障（代码层），第 2 条是软约束（prompt 层）。

**Q3. 工具执行出错了怎么办？比如搜索接口挂了。**

**答**：所有工具都被 `withToolLogging` 统一包装，两层处理：

1. **捕获**：try/catch 捕获异常，带堆栈写日志，同时**给 AI 返回明确的错误字符串**（"工具 xxx 执行出错：xxx，请告知用户稍后重试"），AI 会据此调整行为，而不是整个 Agent 崩溃
2. **超时**：每个工具设置 30 秒显式超时（`timeout` 字段），防止 execute 挂起导致 Agent 卡死

**Q4. 模型幻觉怎么办？比如它编造了一个不存在的笔记 id 去 update。**

**答**：两层兜底：

1. **数据层**：`updateNote`/`readNote` 都带 `.eq("userId", userId)`，RLS 也会强制校验，跨用户/不存在的笔记直接返回错误信息，模型拿到错误信息后会重新 search
2. **提示词约束**：prompt 里明确要求"先 searchNotes 获取 id 再 readNote"，从流程上降低编造概率
3. 用户消息里的 `[@文档标题](文档id)` 提及标记会直接给出真实 id，模型优先用这个

**Q5. 为什么要用事件回调上报副作用，而不是让工具直接改前端状态？**

**答**：因为**工具跑在服务端**（route.ts 里），前端看不到它的内部执行。原来用"共享可变对象 + 轮询"的方式很脆弱（多工具写同一个对象有顺序耦合），我改成**注入式 `onEvent` 回调**：工具副作用发生时上报事件 → agent 层聚合成 SSE 事件队列 → 前端按事件类型驱动跳转/弹框/刷新。显式枚举的事件类型让新增副作用不会漏推，工具之间也没有共享可变状态的耦合。

**Q6. 用户问"把第 3 轮我说的那个需求加进笔记里"，Agent 怎么记住？**

**答**：靠两段上下文：

1. **会话历史注入**：每轮对话的 user/assistant 消息落库，下一轮请求时把**最近窗口内的原文**注入模型（配合上下文压缩，早期消息以摘要形式注入）
2. **全文注入不裁剪**：历史里包含"那篇""这个"等指代，模型结合前文理解。压缩后的早期部分以摘要形式承载关键决策

**Q7. AI 在用户确认删除前能不能继续调用其他工具？**

**答**：不能，我做了强制中断：`onStepFinish` 检测到本轮包含 `deleteNote` 调用且已触发确认后，立即 abort 内部 AbortController 中止生成。**目的**：防止 AI 在用户确认前继续操作（比如先删后建造成误伤）。确认后用户是另起一轮对话让 AI 继续。

### 点 2：长会话上下文压缩

> 滑动窗口保留最近 N 轮对话原文，窗口外历史由模型提炼为重写式摘要，注入时摘要+窗口原文组合，保持 AI 记忆完整性的同时控制 token 成本

**Q8. 用户聊了 200 轮，模型每轮能看到什么？**

**答**：结构是「摘要 + 窗口原文 + 当前输入」：

```
[系统提示词]
[历史摘要]        ← 早期对话压缩成的摘要（800 字符上限）
[最近 100 条原文] ← 滑动窗口保留的原文
[当前输入]
```

- 最近 100 条（约 50 轮）消息**原样保留**
- 更早的消息**压进摘要**：每次压缩触发时，模型把「旧摘要 + 本次滑出窗口的消息」重写为一份新摘要

**Q9. 什么时候触发压缩？**（更新版——改造后）

**答**：改造后是**确定性触发**：每次 assistant 消息落库后 fire-and-forget 检查，当**未压缩消息数超过 100 条**时，把最旧的溢出部分（`length - 100` 条）压进摘要并标记 `compressed`。不再依赖字符阈值，也不再让模型决策"哪些消息留原文"（那是旧版机制）。

**Q10. 为什么选择"窗口 + 摘要"而不是纯滑动窗口或纯摘要？**

**答**（关键题，要讲清 trade-off）：

| 方案 | 优点 | 缺点 |
|---|---|---|
| 纯滑动窗口（只留最近 N 轮） | 实现简单、无开销 | 硬截断，早期关键信息**永久丢失**（金鱼记忆） |
| 纯摘要（全部压成摘要） | 完全不丢语义 | 摘要丢失细节，模型每次都要读一遍全量摘要 |
| **窗口 + 摘要（我的方案）** | 近期对话保真 + 远期语义不丢 | 需要一次模型调用开销 |

**核心取舍**：近期对话（窗口内）**保细节**，远期对话**保脉络**。摘要记住"用户在做 RAG、选了 Milvus、卡在召回率"，但不会为第 3 轮闲聊花 token。

**Q11. 压缩是重写式还是拼接式？**

**答**：**重写式**。每次压缩把「旧摘要 + 本轮滑出的消息」一起喂给模型，生成**一份完整的新摘要**，覆盖旧摘要。不增量拼接——避免摘要越拼越长，也避免过期信息残留。

**Q12. 压缩失败会不会损坏对话？**

**答**：不会，设计了**失败降级**。任何一步失败（模型 API 异常、摘要输出无效、解析失败）都只是打日志，本轮不压缩、不动数据，下次落库会重试。压缩永远"宁可不压，不可压坏"。另外**先写摘要再标记消息**——摘要落库失败则消息保持未压缩（下次重试），不会出现"已标记 compressed 但没有摘要"的中间态。

**Q13. 会不会出现两个压缩任务同时跑，把摘要写乱？**

**答**：不会，我做了**按会话串行化**。压缩是后台 fire-and-forget 触发的，多轮对话可能重叠触发。我维护了一个会话级别的 **Promise 锁链**（`sessionLocks` Map）：新的压缩排在上一轮完成后执行，同一会话的压缩永远串行，杜绝"旧快照晚完成覆盖新摘要"导致已标记消息内容永久丢失。

**Q14. 摘要丢失细节怎么办？比如用户在第 5 轮提到的文档 id 摘要里没记。**

**答**：这是摘要的固有 trade-off，我做了缓解：

1. **摘要生成 prompt 强制要求**：必须保留文档标题与 id（`[标题](id)` 格式），这是后续 readNote 定位的关键
2. **窗口本身保留近期原文**：真正重要的近期信息根本不会进摘要
3. **1M 上下文兜底**：模型上下文窗口大，窗口可以开很大，需要细节时靠 searchNotes 工具精确检索

**Q15. 模型上下文 1M，为什么还要压缩？**

**答**：**省钱 + 省延迟**，不是省"塞得下"：

1. 每轮对话历史全量重发，输入 token 直接决定成本——早期 90% 的对话变成 800 字符摘要后，每轮成本降一个量级
2. 输入越短，首 token 延迟越低，长对话体验更好
3. 上下文窗口是兜底能力，不是默认每轮塞满——塞满 1M 一轮的成本非常惊人

**Q16. 窗口大小为什么是 100 条？**

**答**：100 条 ≈ 50 轮对话，在 1M 上下文下约占 5%-15%（中文编码效率约 1 字 ≈ 1 token）。既保留了充分的近期对话原文，又不至于挤占上下文。如果消息普遍很短可以调大，普遍很长可以调小——当前值在"记忆保真度"和"成本"之间取平衡。代码里是常量 `WINDOW_SIZE`，想调只需改一处。

**Q17. 压缩后前端聊天记录还完整吗？**

**答**：完整。压缩只影响**注入模型的上下文**（`getChatHistory` 带 `uncompressedOnly` 过滤 + limit），前端渲染聊天记录用的是全量拉取（不带过滤），历史消息一条不丢。

### 点 3：加载性能优化

> 针对文档列表渲染瓶颈，实现 React.memo + useRef 稳定回调引用减少无效重渲染；getById 内存缓存 + 请求去重，已访问文档秒开；Supabase 数据库复合索引加速查询

**Q18. 侧边栏文档列表为什么慢？你是怎么定位到瓶颈的？**

**答**（先讲分析思路，再讲方案）：

- **结构问题**：文档是自引用无限层级（`parentDocument`），侧边栏递归渲染每个文档节点。文件多时（几百篇），每篇文档的 `onClick`/`onExpand` 回调如果每次渲染都新建函数引用，`React.memo` 就会失效——memo 靠引用比较跳过重渲染，引用一变就得重渲染
- **方案**：`useRef` 缓存回调——`clickHandlers.current[docId]` 首次创建后复用，`Item` 组件用 `memo` 包裹，props 引用不变时直接跳过重渲染。递归渲染树从"每次展开都要重渲染整棵子树"变成"只重渲染真正变化的节点"

**Q19. 文档详情页的"秒开"是怎么做到的？**

**答**：三层缓存 + 去重：

1. **`getById` 内存缓存**：已加载过的文档直接返回缓存，不重复请求
2. **`pendingById` 请求去重**：同一文档同时被多个组件请求（Navbar 和页面都拉），只发一个请求，其余共享同一个 Promise
3. **缓存上限 + 淘汰**：`DOC_CACHE_MAX = 200`，超出淘汰最旧条目，防止长期会话内存无限增长
4. **悬停预加载**：鼠标悬停侧边栏文档时 `prefetchById` 静默拉取内容到缓存，点击瞬间命中

**Q20. AI 修改了文档，为什么前端还是旧内容？**

**答**：这是缓存一致性问题。`updateNote` 是**服务端直接写库**，不走前端的 `update()`，内存缓存还存着旧值。我加了个 `getByIdFresh`：先 `docCache.delete` 再重新拉取，AI 的 `note_modified` 事件会触发前端调用它刷新。前端自己改文档时，`update()` 里也会主动失效缓存。

**Q21. 数据库查询怎么加速？**

**答**：加**复合索引**贴合查询模式：

```sql
CREATE INDEX idx_documents_sidebar ON documents ("userId", "isArchived", "parentDocument", "createdAt" DESC);
CREATE INDEX idx_documents_id_user ON documents ("id", "userId");
```

- 侧边栏查询按「用户 + 未归档 + 父文档 + 时间倒序」，第一个索引正好覆盖这条查询路径（左前缀匹配）
- 单文档查询按「id + userId」，第二个索引覆盖
- 本质是让查询走索引而不是全表扫描

**Q22. AI 流式回复很卡，怎么优化的？**

**答**：**rAF 节流 + 事件分通道**：

1. SSE 文本 chunk 到达频率可能高于帧率，直接 setState 会一帧多次渲染。用 `requestAnimationFrame` 节流——`pendingStreamingRef` 存最新文本，**每帧最多一次 setState**
2. 流结束时 `cancelStreamingFlush` 取消未执行的 rAF，防止"幽灵流"残留
3. 事件（progress/note_created 等）与文本**分通道**传输，互不干扰

**Q23. 为什么 AI 生成结束后前端会出现重复气泡（幽灵流）？**

**答**：这是流状态管理的经典 bug。我做了两处处理：

1. 流结束/中止时 `cancelStreamingFlush` 取消排队中的 rAF 回调，否则回调在下一帧执行会把 streaming 置回最后一段文本，消息列表下方残留重复气泡
2. abort 分支区分"用户主动停止"和"切换会话导致的中止"：只有同一会话的主动停止才保留已生成的部分内容并提示

**Q24. 你说做了索引，那为什么查询还是慢？索引失效的情况你知道吗？**

**答**（八股转前端性能，见第三部分 Q 扩展）：索引失效的典型场景：对索引列做函数运算（`LOWER(title)`）、前导通配符（`%xxx`）、隐式类型转换、OR 条件未覆盖所有索引列。`searchNotes` 里我特意对 `%_` 做了转义再 ILIKE——虽然 `%keyword%` 是前导通配符无法走普通 B-tree 索引，但至少保证特殊字符不会扩大匹配范围。

## 第二部分：项目深挖

### 架构与技术选型

**Q25. 为什么选 Next.js + Supabase，而不是纯前端 + 自建后端？**

**答**：

1. **Next.js App Router**：路由约定（`app/(main)` 主界面 / `(marketing)` 着陆页 / `(public)` 公开预览）+ 服务端 API 路由（`/api/ai/chat` 流式接口）同仓部署，`middleware.ts` 做全局路由守卫。项目目前全部组件是 `"use client"`，尚未用 RSC
2. **Supabase**：托管 PostgreSQL，自带 **Auth（邮箱注册登录）+ RLS 行级安全 + Storage（文件上传）**，一个平台解决认证、数据库、权限三件事，省去自建后端和鉴权的工作量
3. **代价**：受限于 Supabase 的 RLS 模型，复杂权限（如文档共享）要在 RLS 策略里写，不如自建后端灵活——这是我能讲出来的 trade-off

**Q26. 数据库只有一张 documents 表，怎么支持无限层级嵌套？**

**答**：**自引用外键**。`documents.parentDocument` 引用同表 `documents.id`，配合 RLS 的 `userId` 隔离，天然支持树形结构。归档/恢复时**递归处理子节点**（`archive`/`restore` 里先递归子文档）。侧边栏用 `getSidebarAll` 一次性拉全量（不含正文），前端本地按 `parentDocument` 建树，避免 N 次查询。

**Q27. RLS 怎么做用户隔离的？服务端 AI 工具写库为什么不会撞 RLS？**

**答**：

1. **RLS 策略**：所有表（documents/chat_sessions/chat_messages）都启用了 RLS，策略是 `auth.uid() = "userId"`——用户只能操作自己的数据
2. **双保险**：服务端 AI 工具不仅靠 RLS，还在查询里显式 `.eq("userId", userId)`，双写条件，即使 RLS 被绕过也不会跨用户
3. **一个坑**：`chat_messages` 的压缩任务需要 UPDATE 权限，原策略只有 SELECT/INSERT——我加了个 `chat_messages_update_own` 的 UPDATE 策略，否则 PostgREST 对无权限 UPDATE 返回静默空数据，压缩会"看似成功"实则失效

**Q28. Agent 架构整个链路是怎么串起来的？画一下。**

**答**：

```
用户输入 → ai-panel.tsx (前端)
  → POST /api/ai/chat (route.ts)
      → 落库 user 消息（requestId 幂等防重）
      → 拉会话历史（uncompressedOnly + limit 100）
      → runNoteAgent (lib/agent.ts)
          → streamText(model, messages, tools, system)
          → 工具副作用 → onEvent → 事件队列
      → SSE 流返回 (text/progress/note_created/confirm_delete/note_modified/references/error)
  → ai-panel 解析 SSE 事件分通道渲染
  → 流结束 → 落库 assistant 消息 → 触发 maybeCompressSession (后台压缩)
```

**Q29. 为什么 requestId 幂等用数据库唯一约束，而不是进程内 Map？**

**答**：两种方案对比：

- **进程内 Map**：部署为 Serverless/多实例时，每个实例内存不共享，Map 防不住跨实例的重复请求；还有内存泄漏风险
- **数据库唯一约束**：`chat_messages(userId, requestId)` 建唯一索引，重复插入触发 `23505` 冲突 → 返回 409。数据库约束天然全局共享，且没有内存问题

**Q30. SSE 事件为什么按 `\n\n` 分隔解析？直接拼接文本不行吗？**

**答**：SSE 协议本身就是 `data: <json>\n\n` 的事件流格式。我设计成**事件与文本分通道**：

- `text` 事件只携带流式文本增量
- `progress`/`note_created`/`confirm_delete`/`note_modified`/`references` 是独立事件，前端按类型分发

如果混在文本里靠正则提取标记，会有边界问题（AI 生成的内容本身可能包含相似的标记文本），也难扩展。前端按 `\n\n` 分隔事件行，每行 `JSON.parse` 后 switch 分发，**明确、可扩展**。

**Q31. confirm_delete 确认流程的竞态你怎么处理的？**

**答**：删档确认链路涉及「AI 发起删除 → 前端弹确认框 → 用户确认 → 前端真删」。关键竞态是：**AI 在用户确认前不能继续调用其他工具**。处理：

1. Agent 层：`onStepFinish` 检测到 `deleteNote` 已触发确认 → **立即 abort**，中断本轮生成
2. 前端层：确认框状态由 `confirmingDeleteId` 管理，确认后调 `remove()` 落库；跳转前先 `getById` 确认文档存在，已删除的提示而不跳转（避免 not found 页）

### 工程实践与防御

**Q32. 你提到了"复用旧框架"，具体是怎么迁移的？**

**答**：项目最初基于 Clerk + Convex + EdgeStore，后来**迁移到纯 Supabase**。迁移方式是**接口层不动、实现层替换**：

- 所有数据访问收敛到 `lib/db.ts`，组件只调 `db.ts` 导出的函数，不直接写 Supabase 查询（AGENTS.md 约定的架构纪律）
- 迁移时只需替换 `db.ts` 内部实现，上层组件完全无感
- 好处：数据层可替换、可测试，迁移成本低

**Q33. 你写了很多单测，测试策略是什么？**

**答**（对应 AGENTS.md 的约定）：

1. **后台代码必须补测试**：`lib/`、`app/api/` 每次修改都要有对应用例
2. **同构目录**：`test/lib/`、`test/api/` 与被测模块目录同构
3. **不连真实数据库**：supabase / ai sdk / logger 全部 `vi.mock` + fake 桩
4. **重点测纯函数和边界**：`buildCompressPrompt`/`extractSummary` 等纯函数好测，并发串行化（两次并发只触发一次锁链）、降级路径（模型异常不抛错）这些**最容易出 bug 的地方**必须有用例

**Q34. 上下文压缩改造前有个 30,000 字符的触发阈值，为什么改成确定性窗口？**

**答**（改造动因，要讲清楚）：

- **旧版**：字符阈值触发 + 模型决策 keep（模型挑哪些消息留原文）。灵活但有两个问题：一是**触发时机不稳定**（消息长短影响触发时机，行为不可预期）；二是**模型决策不可控**（模型可能把关键消息压掉或全保留，靠保真地板/keep 上限硬约束补救）
- **新版**：**确定性窗口**——未压缩消息超过 100 条就压最旧溢出部分。行为可预期：**"最近 50 轮保原文，更早的进摘要"**，正是业界"滑动窗口控长度 + 摘要保留脉络"的标准组合。模型只负责总结，不参与决策，代码大幅简化（去掉 keep 解析和硬约束逻辑）

**Q35. 这个项目你最大的难点 / 最值得讲的是什么？**

**答**（开放题，展示思考深度）：

1. **压缩的一致性**：摘要重写、消息标记、并发串行化、失败降级——压缩是后台异步任务，最容易出现"标记了但摘要没写""两个压缩任务写乱"这类数据一致性问题。我的解法是"先写摘要再标记 + 会话级锁链 + 任何失败降级"
2. **AI 与应用的解耦**：Agent 的副作用（删档确认、跳转、刷新）通过事件流通知前端，而不是共享可变状态，前端状态机（rAF 节流、会话切换竞态、队列调度）都是围绕流协议设计的
3. **缓存一致性**：服务端写库 vs 前端缓存的矛盾（`getByIdFresh`）

## 第三部分：从项目难点扩展的前端八股

> 面试官常从你的项目引出一个知识点，然后展开追问。这里把每个点提前铺好。

### React 渲染性能

**Q36. React.memo 的原理？在什么情况下 memo 没用？**

**答**：`memo` 是**浅比较 props** 的高阶组件。`Object.is` 比较每个 prop：

- props 是 `string`/`number` 等原始值 → 值相同则跳过
- props 是函数/对象 → **每次渲染都是新引用**，比较永远不等，memo 失效

所以"函数组件里内联定义 `onClick={() => ...}`"会让 memo 完全失效——这正是我在 `document-list` 里用 `useRef` 缓存回调的原因。

**Q37. useCallback 和 useRef 缓存回调有什么区别？**

**答**：

- `useCallback(fn, deps)`：deps 变化时**重新创建**函数，适合"依赖 props/state"的回调
- `useRef`：**创建一次永久复用**，适合"完全不依赖变化值"的回调（如 `() => router.push(id)`，id 在闭包里固定）

我的场景是"每个文档 id 对应一个固定回调"，用 useRef 更贴合（且不依赖 deps 数组）。如果回调依赖会变的值（如 `level`），就得用 useCallback 并声明依赖。

**Q38. 什么是渲染节流？和防抖/节流（debounce/throttle）有什么区别？**

**答**：

- **防抖（debounce）**：最后一次触发后延迟执行（如输入框搜索）
- **节流（throttle）**：固定时间间隔执行（如滚动事件）
- **rAF 渲染节流**（我的用法）：把 setState 合并到**每帧最多一次**。因为 React 渲染本身和浏览器帧对齐，高频 setState 一帧内多次调用会被合并成一次渲染（React 18 自动批处理），但**每次 setState 都会触发一次 render 调度**，对于重组件（ReactMarkdown 全量重解析）仍有成本。rAF 让"最新文本每帧只渲染一次"，中间帧的中间文本直接跳过

**Q39. React 18/19 的自动批处理（automatic batching）了解吗？**

**答**：React 18 起，**所有**更新（含 Promise 回调、setTimeout、原生事件）默认自动批处理，一帧内的多次 setState 合并成一次渲染。但要注意：**批处理只是合并渲染，不是取消计算**——每次 setState 依然会创建新的 fiber/执行组件函数体。所以"多个 setState 是 OK 的（批处理），但高频 setState 仍需 rAF 节流（减少 render 调度和 DOM 更新成本）"。

**Q40. 虚拟列表了解吗？为什么项目没用？**

**答**：虚拟列表（react-window 等）只渲染可视区域的行，适合**长而扁**的列表。我的侧边栏文档树有两个特点让它不划算：**层级递归结构**（每个节点有折叠展开状态，行高不定）+ **规模可控**（几百篇文档，全量渲染 1000 个以内的节点成本可接受）。我选择用 memo + 稳定引用减少**重渲染成本**，而不是减少**渲染数量**——对于这个规模，后者优化收益低、实现复杂度高。

### 前端状态管理

**Q41. Zustand 和 Context 有什么区别？为什么选 Zustand？**

**答**：

| 维度 | Zustand | Context |
|---|---|---|
| 渲染触发 | selector 订阅，**只有选中的 slice 变化才重渲染** | value 变化所有消费组件重渲染 |
| 心智 | 独立 store，模块化 | 需要 Provider 嵌套 |
| 使用 | `useRefresh(s => s.sidebarKey)` 精准订阅 | `useContext` 拿全量 |

我的 `useRefresh` store：`triggerSidebar()` 只 +1 `sidebarKey`，`triggerDocument(id)` 只更新单个 `documentKeys[id]`——消费组件各自订阅，**AI 改文档时只刷新那一个文档的组件，侧边栏整体不重渲染**。如果用 Context，一次触发全量重渲染。

**Q42. Zustand 的 selector 返回新对象会不会导致死循环？**

**答**：会。`useRefresh(s => ({ k: s.sidebarKey }))` 每次 selector 返回**新对象引用**，Zustand 用 `Object.is` 比较，永远不等 → 无限重渲染。解法：selector 返回原始值（`s => s.sidebarKey`），或配合 `useShallow`。我的代码里 selector 都是返回 `number`/函数引用，规避了这个问题。

### HTTP 与流式协议

**Q43. SSE 和 WebSocket 的区别？什么场景用哪个？**

**答**：

- **SSE（Server-Sent Events）**：HTTP 单向流，服务端→客户端，**自动重连**（EventSource 原生支持），基于普通 HTTP 好部署
- **WebSocket**：双向全双工，客户端也能推服务端，需要握手 + 连接管理

**场景选择**：我的 AI 流式生成是「服务端→客户端单向推送 + 客户端只发一个请求」，SSE 天然契合；且服务端在 Serverless 上 SSE 比 WS 好实现。WebSocket 适合聊天室（双向实时）这类场景。

**Q44. fetch 流式读取和 ReadableStream 了解吗？**

**答**：`fetch` 返回的 `response.body` 是 `ReadableStream<Uint8Array>`，用 `getReader()` 逐块读：

```js
const reader = response.body.getReader();
const decoder = new TextDecoder();
while (true) {
  const { done, value } = await reader.read();
  if (done) break;
  buffer += decoder.decode(value, { stream: true });
  // 按 \n\n 切分事件行
}
```

**关键**：`decoder.decode(value, { stream: true })` 处理**多字节字符跨 chunk 截断**（一个中文 UTF-8 字符被拆在两个 chunk 时，`stream: true` 会保留不完整的字节等下一段）。我前端解析 SSE 就是这套，buffer 按 `\n\n` 切分。

**Q45. 服务端流式响应为什么用自定义 ReadableStream 而不是直接 res.write？**

**答**：我封装了一个 `ReadableStream` 手动 enqueue：**事件队列轮询 + pull 驱动读文本流**。好处：

1. **事件与文本分通道**：progress/副作用事件用 setInterval 轮询事件队列立即推送，不等文本 chunk
2. **超时兜底**：每次 `reader.read()` 用 `Promise.race` 包 120 秒超时，流卡死能强制关闭
3. **取消清理**：`cancel()` 回调统一回收定时器，避免泄漏；流关闭时兜底 resolve done Promise，防止 assistant 消息静默不落库

### 工程与安全

**Q46. 数据库复合索引为什么把 userId 放最左？**

**答**：复合索引 `(userId, isArchived, parentDocument, createdAt)` 的匹配遵循**最左前缀原则**——查询条件必须从最左列开始连续匹配才走索引。我的查询都是"某用户 + 条件"，`userId` 放最左保证**所有查询都能命中索引的第一列**（等值条件下 SQL 优化器会用该索引）。如果 `userId` 不放最左，按用户查就退化全表扫描。

**Q47. RLS 和 Next.js Middleware 路由守卫的关系？**

**答**：**双层防御，职责不同**：

- **Middleware**：路由层——未登录访问 `/documents/*` 重定向 `/login`，保护页面渲染（不防数据，因为服务端渲染前也可能被请求 API）
- **RLS**：数据层——即使绕过了 Middleware 或直接调 Supabase API，RLS 在数据库层强制 `auth.uid() = userId`，用户只能读自己的行

**本质**：Middleware 是"门卫"（挡未登录），RLS 是"最后一道锁"（就算进来了也动不了别人的数据）。真正安全兜底是 RLS，Middleware 只是体验优化。

**Q48. 如果文档要支持多人协作/共享，RLS 要怎么改？**

**答**（开放设计题）：

1. 加 `document_shares` 表存"文档 id + 被共享 userId + 权限（读/写）"
2. RLS 策略从 `auth.uid() = userId` 扩展为：
   ```sql
   auth.uid() = "userId" OR auth.uid() IN (SELECT "userId" FROM document_shares WHERE "documentId" = id)
   ```
3. 写操作还要区分读/写权限（写 = 拥有者或共享为写）
4. 代价：RLS 子查询每次访问都执行，要考虑索引；复杂权限逻辑建议收敛到 Postgres 函数

**Q49. 为什么测试不连真实数据库？**
